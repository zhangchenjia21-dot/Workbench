## 判断与选择

当前产品主要把 Owner 手工输入按日期排列，输入端与真实工作断开。UAT 已修好日历交互，但原定义的“低维护”与避免 Calendar/Todo 化仍没有闭环。

| 方向 | 价值 | 复杂度/维护成本 | 决定 |
|---|---|---|---|
| 手工粘贴 ChatGPT/项目文档再整理 | 通用，但仍要求反复搬运且无可靠增量来源 | 低入口成本，持续人工成本高 | 不选 |
| 本地 Git 工作区变化 | 真实、无账户，适合编码现场 | 路径/分支/机器绑定，无法直接获知云端验证与待评审工作 | 暂不选 |
| GitHub 项目近况 → 可确认 Track 更新 | 一次连接，跨设备产生的提交/PR/验证直接出现；有清楚证据与状态差异 | 官方只读 API，先支持公开仓库、有限拉取，不管理账号令牌 | 选择 |

## 体验

Today 增加“项目近况”，以新增外部变化而非日历任务组织；Current Vector 保持独立只读。Sources 页面连接最多 3 个 GitHub 公开仓库、首次获取、手动刷新、后台每 30 分钟检查、查看原始证据、已读和断开。相同证据去重，不重复制造“新变化”。失败保留上次快照并明确陈旧时间。

基于确定性事实规则提炼：当前主线提交、提交标题、开放 PR（draft 与可评审分开）、当前 SHA 对应的 Actions。验证通过不等于产品 PASS，提交数量不等于个人进度。无需 LLM 或向外上传个人状态。

Owner 可从一条近况直接创建 Track，或明确选择已有 Track。显示原值和可编辑的“当前真实状态/近期方向”，确认后才写入；不猜测关联、不更改目标/阶段/生命周期、不生成 Plan。外部证据和 Track 都存在同一本地 SQLite，分别表达“观察到什么”和“Owner 认可的状态”。Today 只投影，不存第二份事实。

## 实现边界与检验

个人状态模块 L0：来源快照/提炼规则；L1：固定 GitHub API 读取与校验、追加 schema；L2：快照入库/去重/确认事务；L3：读写公开接口与异步刷新隔离。UI 在桌面界面 L3，Bootstrap 注册 IPC 和后台定时。无需新平台模块。

追加 v4 两张来源/近况表，旧 DDL 不改，仍沿用 safety + ordered migration + validation + staging/restore。异步请求在恢复/关闭后不得写入旧结果；同源请求合并；Track 或近况在确认期间发生变化则拒绝旧提案。网络/认证/速率限制不影响现有本地核心。
